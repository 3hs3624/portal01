## 문서의 읽는 방법과 완전성 기준

앱별 문서는 화면 구획 → 사용자 조작 → 입력·기본값 → 결과·저장 → 예외·권한 → 코드·검증 순서로 읽습니다. 화면별 표는 화면 문구를 나열하는 데 그치지 않고 클릭·입력·취소·다시 열기·스크롤·드래그 후의 상태를 명시합니다. 정적 컨트롤의 ID·속성·선택지는 인벤토리에서 대조합니다. 동적으로 생성되는 행·열·차트·권한 버튼은 생성 모듈 및 명령 목록과 앱별 흐름을 함께 봅니다.

현재 구현, 설정/브라우저 의존 기능, 계획 단계 기능을 구분합니다. 예를 들어 AI 응답 생성, 실시간 동시 타이핑 병합, 로컬 SQLite, 서명된 설치판·자동 업데이트는 현재 완료 기능으로 기록하지 않습니다. 테스트 파일의 존재는 실운영 계정·모든 단말의 검증 완료를 의미하지 않습니다.

## 변경 시 갱신 절차

1. 화면·문구·입력·권한·저장·오류·배포에 영향을 주는 변경의 설계서 범위를 정합니다.
2. 같은 커밋/PR에서 해당 설계서를 수정합니다. 제거 기능은 현재 사양에서 제거하고 변경 이력에 남깁니다.
3. UI 정의를 바꿨으면 `python scripts/design_inventory.py`로 인벤토리를 재생성합니다.
4. `CHANGELOG.md`에 날짜, 실제 동작, 영향 파일, 검증 결과 또는 미검증 범위를 기록합니다.
5. `python scripts/check_design_docs.py --base <기준 커밋> --head <변경 커밋>`과 `python scripts/design_inventory.py --check`를 실행합니다.
6. 웹/설치형에 공통 기능을 반영할 때 두 브랜치의 설계서도 같은 변경으로 맞춥니다. 문서만 바꾼 작업은 앱 배포나 OS 빌드 재실행을 요구하지 않습니다.

자동 검증은 문서 갱신 누락과 코드 인벤토리 불일치를 탐지합니다. 실제 UX 설명의 정확성은 코드·화면 검토로 확인해야 합니다. 컨트롤 ID나 명령이 늘면 인벤토리만 갱신하는 대신 해당 동작·빈 상태·실패 상태도 본문에 추가해야 합니다.
