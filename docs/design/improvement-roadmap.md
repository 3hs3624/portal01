## 1. 권고 결론

우선순위는 ①배포 전 업무 회귀와 복구 검증 ②공유본/개인본의 명확한 사용·복원 ③설치형 핵심 업무 완성 ④앱별 편집/엑셀/분석 품질 ⑤설치형 로컬 저장·정식 배포입니다. 새 차트·AI·실시간 동시 타이핑보다 현재 작성한 자료를 잃지 않고 같은 방식으로 열고 저장하는 흐름을 먼저 완성합니다.

이번 작업은 코드·기존 설계의 정적 검토와 계획 작성입니다. 신규 기능 구현·운영 DB/권한 변경·사용자 데이터 전송·실제 성능 측정을 수행한 것으로 기록하지 않습니다. 아래 시간과 수치는 계획 추정/검수 목표이며 측정된 성능이 아닙니다.

## 3. 개선 백로그와 우선순위

## 4. 항목별 구체 계획

### E01. 핵심 업무 시나리오를 릴리스 기준으로 만들기

근거: 현재 확인한 명시적 CI는 설계서 검사와 설치형 policy/stage/로그인 셸/리사이저 smoke/패키징입니다. 기능별 브라우저·SQL 테스트는 존재하지만 이 검토에서 릴리스 전체 업무 관문의 자동 실행을 확인한 것은 아닙니다.

작업: 기존 저장·공유·표·보기·엑셀 테스트를 빠른 PR 묶음과 전체 릴리스 묶음으로 나눕니다. OS별 실제 사용자 업무 smoke를 별도로 추가합니다. 실패한 commit은 배포를 막고 이전 검증 artifact로 되돌리는 절차를 기록합니다. UI 스냅샷만으로 데이터 왕복을 판정하지 않습니다.

완료 기준: 세 앱의 생성→편집→저장→닫기→재열기, 공유 조회/편집/회수, 충돌, WBS Excel 왕복이 fixture 데이터로 검증됩니다. 실패 주입 시 성공 표시가 나오지 않아야 합니다. 릴리스 보고서에 commit·환경·실행 시나리오·실패/미검증 범위를 남깁니다. 운영 사용자 데이터·메일은 사용하지 않습니다.

### E02. 실제 복구 가능한 백업

근거: 최근10개 자동/수동 백업이 같은 브라우저의 IndexedDB에 있고 외부 반영은 수동입니다. 같은 프로필의 백업만으로 브라우저 데이터 제거까지 보장하지 않습니다.

작업: 저장소 화면에서 현재 작업 위치, 복구본 위치, 마지막 외부 백업 시각과 복원 시험 결과를 구분합니다. 사용자가 명시적으로 선택한 폴더/내려받기 경로에 복구본을 보관하고, 주기/보관 수 정책을 설정할 수 있게 설계합니다. 외부 자동 백업은 기본 꺼짐으로 두고 위치·권한·실행 주기와 실패 표시를 확인한 뒤 사용자가 켜게 합니다. 브라우저 제약으로 실행할 수 없는 백그라운드 백업을 완료로 표시하지 않습니다.

완료 기준: fixture를 새 브라우저 context/새 설치형 profile로 복원해 ID·문서/폴더·BI 연결·PM 이력/Excel 템플릿을 semantic 비교합니다. 손상/잘못된 계정·버전·용량 초과는 기존 작업을 유지한 채 거부합니다. 목표 복구 시간은 대표 fixture에서5분 이내로 정하되 데이터 크기별 실측 후 확정합니다. 원래 프로필을 실제로 지우는 운영 시험은 하지 않습니다.

### E03. 공유 대상과 버전 복원

근거: 개인 행 열기가 기존 공유 연결을 열고, 공유본은 개인 원본과 별도입니다. shared_versions에 이전3개가 보관되지만 현재 공유 action에는 사용자용 이력 조회/복원 API가 없습니다.

작업: 소유자에게 ‘개인 원본 열기/공유 작업공간 열기’를 명확히 구분합니다. 개인본→공유본 반영은 자동 동기화가 아니라 변경 비교 후 명시 반영으로 설계합니다. 공유본 저장 충돌에서는 내 변경을 보관하고 최신 내용과 비교합니다. 소유자 전용 버전 목록·미리보기·현재본 백업 후 복원 action을 도입합니다.

권한 결정: 초기 이전본 조회/복원은 소유자로 제한합니다. 나중에 참여한 사용자가 부여 전 기록까지 보게 되는 정책은 별도 결정 전 허용하지 않습니다. edit 사용자의 현재본 쓰기 권한과 이전 버전 복원 권한을 혼동하지 않습니다. 보관3개를 무제한 이력처럼 표시하지 않습니다.

완료 기준: 개인본과 공유본의 ID/저장 위치를 UI와 테스트에서 구별합니다. 복원은 expected revision으로 보호하고, 권한 회수·타 계정·부여 전 과거 기록 접근을 거부합니다. 부분 실패와 네트워크 중단 후 내 변경을 회수할 수 있어야 합니다. 실시간 동시 타이핑은 이 단계 범위가 아닙니다.

### E04. 설치형 핵심 업무를 먼저 완주

근거: desktop/src/main.cjs는 Insight 상세 창만 명시 허용하고 다른 새 창은 거부하며 permission 요청은 기본 거부입니다. 현재 스모크는 전체 WBS/인증/네이티브 파일 업무 검증을 대신하지 않습니다.

작업: HostBridge의 최소 계약(허용된 파일 선택/원자 저장/앱 창/상태)을 정합니다. WBS의 부모/opener 의존을 명시적 메시지·수명주기 관리로 옮겨 허용된 프로젝트 새 창만 열리게 합니다. 로그인 Origin·Redirect·세션 복원 정책을 검증하고 웹에서는 기존 adapter를 사용합니다. renderer에 임의 fs/shell/SQL 권한을 주지 않습니다.

완료 기준: Windows/Linux/Mac Intel/ARM에서 로그인→문서 저장→프로젝트 등록→WBS 열기→Excel 업로드/다운로드→폴더 저장→앱 재실행→복원을 테스트합니다. 한글 IME/창 닫기/부모 창 종료/중복 창/경로 이동 실패도 확인합니다. 허용 범위 밖 새 창은 계속 막습니다. 파일 기능을 지원하지 못하는 환경은 웹 대체 동작과 미지원 사유를 표시합니다.

진행 판단: 각 OS 검증이 막히면 E09 정식 배포로 넘어가지 않고 웹 기능은 유지합니다. 우선 한 OS에서 수직 시나리오를 통과시킨 뒤 나머지 OS로 확장합니다.

### E05. Excel 보존 검사를 의미 비교로 확장

근거: 현재 inspect는 수식·조건부 규칙·서식 셀 개수 감소를 검사합니다. 개수가 같아도 참조식이나 적용 범위가 달라질 수 있습니다. 원본 보존 코드의 구조 판정은 layout kind 배열을 비교합니다.

작업: 허용된 입력 셀 변경과 보존해야 할 XML 부분을 구분하고, 수식 식/참조·조건부 sqref/우선순위·style 의미·병합·숨은 ID·행/열 크기·사용자 시트를 비교합니다. task ID/순서/종류 변경에 대한 원본 보존 가능 판정을 명확히 합니다. 구조 변경은 새 양식 경로임을 미리 안내합니다. 실제 잘못된 결과가 있다고 단정하지 않고 재현 fixture부터 추가합니다.

완료 기준: 서로 다른 WBS 양식 최소5종, 한글/중복 이름·태스크 순서 변경·수식 같은 개수 다른 내용·조건부 적용 범위 변경을 포함합니다. Excel 실기기 재계산 후 간트/수식과 허용된 수정 셀을 확인합니다. 보존 불가면 이유와 원본 복구 경로를 안내하고 조용히 손실시키지 않습니다.

### E06. Write Studio 반복 입력과 삭제 복구

작업: 문서/폴더 삭제의 휴지통·복원 정책을 정하고 기존 편집 undo와 구분합니다. 일반 표/DB에서 Tab·Shift+Tab·Enter·Esc·다중 셀 붙여넣기·선택 범위·삭제/이동 후 포커스 규칙을 통일합니다. 모든 뷰를 일시에 다시 만들지 않고 표 보기부터 검증합니다. 직접 편집 옵션과 공유 조회 제한을 유지합니다.

완료 기준: 한글 조합 중 중복 행 생성 없음, 붙여넣기 실패 시 원래 셀 보존, 같은 undo로 관련 행/필드가 복원됩니다. 삭제 복원 시 폴더/연결/댓글/보기 설정이 유지됩니다. 키보드만으로 대표 표/DB 작성 시나리오를 마칩니다. 기존 페이지 열기 side/center/full와 헤더 이동 잠금을 회귀 검증합니다.

### E07. Insight BI 교체 미리보기와 성능

작업: 데이터 교체 전 추가/삭제/이름/타입 변경 열과 영향 대시보드/카드를 보여주고 열 mapping·취소·비교 후 적용을 제공합니다. 큰 데이터는 먼저 파싱·필터·집계·차트 재생성의 시간을 측정합니다. 결과에 따라 Worker 계산, 표 가상 스크롤, 변경 카드만 다시 그리기를 순차 적용합니다. 임의 샘플링으로 합계가 달라지지 않게 합니다.

완료 기준: 1천/1만/10만 행과 고정20열 fixture를 기준 PC에서 측정하고 넓은 열 데이터는 별도 시나리오로 정의합니다. 제안 목표는1만행 필터 p95 500ms 이내, 10만행 작업은 취소/진행 표시와 UI 응답 유지입니다. 목표는 실측 후 확정하며 현재 보장 수치가 아닙니다. 메인/Worker 계산 결과와 원본 행이 일치하고 실패한 교체는 원본을 유지합니다.

### E08. 설치형 로컬 데이터와 오프라인

작업: SQLite·첨부 파일·버전 migration을 Main 서비스에서 관리하고 앱별 데이터 모델은 기존 원형/관계형 adapter에 연결합니다. JSON·기존 Electron/브라우저 profile을 사전 백업→검증→이전하고 실패 시 기존 저장소로 돌아갈 수 있게 합니다. 토큰은 OS 보안 저장소로 분리합니다. ‘오프라인에서 무엇을 편집할 수 있는가’와 공유 권한 유효 기간을 먼저 결정합니다.

권고 정책: 개인 로컬 작업은 오프라인 편집 가능, 클라우드/공유 반영은 명시적 연결과 권한 확인 후 수행합니다. 자동 양방향 병합·오프라인 공유 수정은 초기 단계에서 약속하지 않습니다. 중복 실행/파일 잠금·강제 종료·반만 쓴 migration을 시험합니다.

완료 기준: 종료 직전 저장과 재실행, DB/파일 일관성, 계정 격리, 기존 자료 왕복·백업/복구를 OS별 검증합니다. renderer 직접 DB 접근을 허용하지 않습니다. 현재 설치형이 SQLite를 이미 사용한다고 문서를 바꾸지 않습니다.

### E09. 정식 설치·업데이트

작업: Windows 서명·Mac 공증/서명·Linux 패키지, 버전/채널/업데이트 검증·migration·실패 복귀, 다운로드/변경 이력을 정리합니다. 인증서·배포 계정은 소유자 준비 항목입니다. 개발 아카이브와 정식 설치 파일을 이름/채널/안내에서 구분합니다.

완료 기준: 깨끗한 기기 신규 설치와 이전 버전 업그레이드·취소/네트워크 단절·복구 시험을 통과합니다. 업데이트 전 자료 백업이 있어야 하며, 저장 schema가 바뀌면 이전 실행 파일만 되돌리는 방식으로 복구를 보장하지 않습니다. 운영 릴리스 전 실제 사용자 베타와 체크리스트를 통과합니다.

## 6. 첫 10근무일 제안

- 1~2일: 핵심 시나리오/지원 환경/fixture·복구 데이터 크기 확정, 현재 실패 재현 여부와 실행 시간을 기록합니다.
- 3~4일: 기존 저장·공유·Excel·레이아웃 테스트를 배포 관문에 연결하고 의도적 실패 시 차단을 검증합니다.
- 5~7일: 한 앱에서 외부 복구본→새 profile 복원 시제품을 만들고 상태/실패 안내를 검수합니다.
- 8~10일: 같은 복구 계약을 나머지 앱으로 확장하고 데이터 연결·프로젝트 이력·Excel 원형을 비교합니다. 목표를 넘으면 다음 주에 이어 검증하며 세 앱 전체 완료로 선포하지 않습니다.

첫 배포 범위는 회귀 관문과 검증을 마친 복구 기능입니다. 공유/새 차트/정식 설치판을 같은 첫 배포에 묶지 않습니다.

## 8. 완료 판정·문서·배포

각 항목은 화면/기능/코드/API/테이블 변경, 정상·빈값·취소·권한·실패·충돌·복구 테스트, 웹/지원 OS 영향, schema migration/롤백을 함께 검토합니다. 기능을 추가할 때 기존 네 설계서와 생성 부록·CHANGELOG를 같은 작업에서 갱신합니다. Google Drive는 Portal 폴더의 기존 문서 ID를 확인해 수정하고 중복 생성하지 않습니다. 계획은 이 별도 문서에서 제안/진행/완료를 구분해 관리합니다.

완료 기준은 ‘빌드 성공’ 하나가 아니라 대표 사용자 업무의 데이터 왕복 결과입니다. 일정과 성능 목표는 범위·장비·실측 결과로 재산정합니다. 이번 검토에서는 현재 운영 서비스의 성능 저하나 보안 결함이 새로 확인됐다고 단정하지 않습니다.
